# 当前方向：验证事件确认机制能否稳定改善任务

已完成[事件响应起步试验](../evidence/risk-response/README.md)与[事件优先级对照](../evidence/event-priority/README.md)。真实后果反馈试验此前已收束，不追加调用。

## 本轮结论

在同一事件空间、120秒有效期及安全检查下，比较FIFO、风险优先、保护下一步可执行机会三条规则。42次环境评价，0模型调用、0训练；新种子94003/94012的6条件中，Tour确认4/15段，FIFO与选定的机会优先均确认11/15段，全部安全违规为0。

机会优先仅因开发平均等待约0.0043秒的差异被选中；新确认与FIFO完整派单相同，没有额外收益。新确认只有2次多个合法事件竞争，机会损失数均不能区分候选。因此保留简单FIFO作为事件机制研究基线，Tour仍为项目默认。

## 下一项安排

优先为事件机制本身做更宽的独立条件验证，提前确定不同故障位置、周期相位、持续时间与专业异常的覆盖；健康与误触发条件也要独立报告。记录每个条件可供选择的竞争机会，不能在缺少竞争时宣称新优先级有效或无效。

不要为了制造差异放宽安全约束或改变人员。现有新确认条件现在均为已见材料，不再用它们挑规则。先形成可保持、可解释的有效确认收益，再恢复后果反馈，并补齐共同输入预算、argmin语义及失败后保留有效反馈。

复现本轮：`python -m patrol_rsi prioritize --output runs/event-priority`。输出必须使用新目录；复现不增加独立样本。方案见[固定配置](../configs/event-priority.json)，原件索引和开发/确认全表见本轮交付。
