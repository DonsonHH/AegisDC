# T7 阶段 2 执行口径

采用 `9d6bfd45` 的 r1 登记和 `41709979` 的开发交付。收到用户指定的 32 字节原文件后核对已发布承诺。一份加密传输交给计算节点，在独占的生成记录下解封一次。每个 draw 先伦敦、后荷兰，各族五个十二行块。完整输入保存在私服，公开其字节哈希、实际运行输入哈希、历史匹配及板内匹配。[登记](../r1/registration.json) · [交接回执](handoff.json)

试点采用一个 5 核 CPU 作业。生成输入后等待三份账和总回执在 GitHub 发布。控制端独立重建历史映射并核查十块分母，核实远端提交后交回放行记录。作业读取该记录才启动 5-01 的 P、PERIODIC、ALARM、B、V_COST。批次是一项新作业，按原序分波执行其余 595 个位置；各臂的状态、公共策略进程、材料与预算各自独立。批量时间预留取试点实耗 TotalCPU ×119×1.75，按该作业核数向下取整到分钟，并对照两倍上限。程序、策略、打分和顺序均在查看评分前固定。硬错误保留当前波和后缀，零重试、零替补。分母始终为每族 60 个条件、每块 12 个。周期巡检与强规则 B 作描述性对照。r1 的面板未登记 ORACLE 臂，因此 H3 上该臂的实测均值及事件率未建立。

HA、HB、HC 按 r1 的原配对差、两族等权、五块校正方差、t(4) 区间及三项 Holm 规则判定。遇到缺失或退化沿用登记的 INDETERMINATE 处理。仅描述性重合敏感性采用同一掩码剔除全部五臂，余下原块按各自保留行数重算。存在输入重合的主分析行照常计入。累计缺额 L 为正的条件计为有合成事件，分母按登记保留。

## 等待失败的描述

为了从轨迹辨认 6-02 类现象，在看 H3 评分前固定以下字段。对每个荷兰原条件，按既有维护许可核对 V_COST 是否曾有可在故障前完工的 NR 开工机会。记录最后一个合法开工时点的公开决策帧及实际请求。该帧为 WAIT、V_COST 未及时有效重分组、转供时跳闸且该转供段有缺额，计作“错过预防窗的等待”。另列强规则 B 及时有效重分组、没有跳闸且转供缺额较小的实测配对。再列无故障前有效初检、随后泵操作为 NO_EFFECT 的子集，保留各自的可判分母。该描述不进入三项主判据。[T4b 同类配对证据口径](../../t4b-holdout-confirmation-v2/readback.py) · [T3 代表条件的实测轨迹](../stage1/witnesses.md)

各族分别列所有五臂的 L、人员实耗和事件率。逐条报告未舍入的 V_COST 缺额高于周期巡检的条件。结果只覆盖冻结的两族等权合成设计。现场事故频率与历史可避免性仍未建立。
