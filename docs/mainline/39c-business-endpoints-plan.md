# 39c：先定义业务评价，再执行

2026年11月9日，依据[用户审阅采纳表](../reviews/20261109-user-review/response.md)。**设计草案，尚未冻结工程输入、预算或执行源码；没有新增运行，也不构成39c验收。** 39b已经能执行工单、检查、处置和复查；本项把这些事件与业务评价接起来，随后交39d核查时间尺度，原39的AI对照最后另冻协议。

|要回答的问题|拟定的评价对象与分母|必须保留的状态|
|---|---|---|
|是否误判|预先声明且有确定正常真值的问题事件中，系统明确判断“有故障”的事件比例|外部虚假提示、系统打开疑点、测到异常读数、确认故障分别登记；打开疑点不直接算误报|
|是否漏报|确定故障事件中，在冻结时窗内具有合法可检测机会的事件；计有/无明确判断及首次到达时间|缺测、尚未到达、不可检测、主动暂缓和未知分别计数，不从总表删除；“来不及处置”另列|
|是否提前发现|首次有效系统判断相对故障节点、服务损失节点或处置截止节点的时间差，参照节点分别报告|节点未在窗口观察到时标右删失；不填零、无穷大或声称预防成功|
|检查是否有业务价值|信息到达是否改变后续行动，及相应服务、工时和费用；因果收益另需同条件对照|只更新认识、改变行动、实际改善、无效和有害分别保留；未识别的反事实收益记未识别|
|问题是否被核验关闭|实际处置、复检及服务证据按预定规则进入公开关闭评估，记录首次满足时刻及后续失效/再开|动作完成、症状退去、未确认、验证关闭、接受风险和升级分别计时；接受风险不算物理修复|
|付出了什么|人员移动/门禁/等待/工作、工具占用、处置/测量费用、推理及失败成本分别合计|保守准入预算和实际花费分开；不同单位不直接相加；失败仍占用分母和预算|

以声明的问题事件计数，重复采样和同源副本不能增加事件数。同一情景或共同根因下的多个事件不自动成为统计独立样本，研究独立单位另由后续协议固定。真值标签必须在工程协议中给出目标、判据、适用时间及来源：故障、确定正常、未知；数值阈值只代表声明的状态判据，不能自动推断故障原因。未知事件的数量和占比单列，只有适用分母为零时才报不适用及原因。

“可检测”与“可挽救”分开定义。可检测机会先按方法无关的声明条件固定：适用观测通道或合法检查、可辨识性、可用资源包络和足够的返回窗口；实际有没有派出、证据何时到达另记，不能通过不检查减少漏报分母。实际派工仍只能使用当时已到达的证据，不能因后台有故障就假定调度者知道。可挽救还取决于到场、检查返回、处置延迟与截止时间；资源竞争等实际失败原因保留。工程协议须明确机会起止、判断截止、窗口边界及删失规则，才可计算漏报或提前量。保持所有工况的完整清单，避免只报告具有有利机会的子集。

私有真值只给评价器；调度、任务生成和关闭继续读取决策时的合法证据及声明知识。评价结果不反向进入当次决策。原`verified_closure.py`的公开评估接口与实际人员/处置反馈是复用入口；需要先核对其稳定问题身份如何对应39b动态实例，再固定适配契约，禁止通过手工标记成功绕过复检。

工程工作按以下顺序推进，每个行为先固定独立预期，再用Slurm做红/绿验证：

1. 正常、故障、未知三个事件的评价与机会分母；迟到/复制记录保持同一事件，公开视图不读取私有标签。
2. 将一条实际检查→处置→复查序列接入关闭程序，验证动作完成时仍未关闭、证据到达前不关闭，以及未满足服务/保持条件时仍开放。
3. 负例覆盖无人工、授权失败、不可检测、处置来不及、窗口删失、风险接受与升级；所有成本及未测状态保留。
4. 独立Spec/Standards、适当根回归、图表与新Git交付完成后再验收39c。新图使用实际保存轨迹，详细原件留在服务器。

原180次比较的`closure_program=None`及其未测端点保持。既有数据可用于说明已有轨迹，不能事后改写为原注册的误报率、漏报率或预防收益。需要匹配反事实的新评价，在各自冻结协议中写清输入、调用/时长预算、失败与重试规则；本草案不授予新的研究预算。
